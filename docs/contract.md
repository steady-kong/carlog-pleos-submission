# 데이터 계약과 이관 전략

이벤트의 신호 숫자가 0이 아닌데 앱의 `Double` 표현에서 0으로 소실되거나 유한하지 않으면 가져오기를 거부한다. 신호 숫자 표기는 최대 1,024자다. 일반적인 부동소수점 반올림까지 없애는 것은 아니며, 이 제한은 JSON Schema보다 엄격하다.

`python3 scripts/check-json-contracts.py`는 세 공개 JSON Schema 자체와 예시의 형식, 잘못된 스키마 버전의 거부를 검사한다. 기존 Python에 선택적 `jsonschema` 패키지가 필요하며 자동 설치하지 않는다. Kotlin 단위 시험은 세 예시를 앱에서 가져온 뒤 같은 JSON 의미로 내보내는지 확인한다. 이는 가능한 모든 입력에 대한 스키마와 구현의 완전한 동등성을 보장하지 않는다.

이벤트·차량 관리 JSON과 PWA 백업의 스키마 버전은 JSON 숫자의 정확한 값으로 비교한다. `1.0`과 `1e0`은 1과 같지만 반올림해야만 1이 되는 값은 거부한다. 과도하게 긴 숫자를 처리하지 않도록 버전 숫자 표기는 최대 256자다. 이 길이 제한은 JSON Schema의 일반 숫자 제약보다 엄격하다.

Carlog 웹 백업의 읽기 전용 미리보기는 없는 테이블과 비어 있는 테이블을 구분한다. 누락 테이블은 이름을 표시하고 해당 건수는 확인 불가로 표시하며, 검사 집계는 파일에 들어 있는 항목만 기준이다. 이는 누락이 정상이라는 판정이나 가져오기·복원을 뜻하지 않는다. 원본 백업은 보존해야 한다.

지출 분류·주행거리 출처 집계는 해당 테이블이 없으면 확인 불가다. 영수증 및 파생 주행거리의 원본 연결 검사는 필요한 테이블 중 하나라도 없으면 전체 확인 불가와 있는 자료만으로 계산한 건수를 함께 표시한다. 누락된 원본 때문에 그 건수에 확인 불가 항목이 포함될 수 있으므로 확정된 오류 건수가 아니다.

삭제 표시 `deletedAt`이 null이 아닌 값 중 문자열이 아니거나 공백이면 별도 건수와 집계 신뢰도 경고를 표시한다. 비어 있지 않은 문자열이 유효한 날짜인지는 검사하지 않는다. 이 미리보기는 삭제 상태를 수정하거나 데이터를 가져오지 않는다.

활성 기록의 차량 참조 중 유일하게 일치하는 차량이 삭제 표시된 경우와 여러 차량이 같은 ID를 쓰는 경우를 별도 집계한다. 중복 ID는 활성·삭제 상태에 관계없이 모호한 참조로 분류하며, 이 수치는 이관 가능성의 보증이 아니다.

활성 영수증의 원본 종류·ID·차량 ID가 유일한 활성 원본 주유·정비·지출 기록에 연결되는지 미리보기에서 집계한다. 반대 방향으로 활성 기록의 `receiptImageId`가 유일한 활성 영수증과 같은 차량·기록 종류·ID로 연결되는지도 별도로 집계한다. 이 검사는 영수증 이미지 내용이나 실제 파일 복원을 확인하지 않는다.

전용 Pleos AVD의 Compose 테스트 호스트에서 이벤트 JSON·차량 관리 JSON·웹 백업의 파일 선택 버튼을 누른 뒤 URI 없는 반환에 대한 안내를 확인했다. 실제 파일 선택과 가져오기는 이 시험에서 검증하지 않았다. 이 선택형 진단은 `MileageScreenTest#importPickerCancellationMessagesAppearOnPleosProbe`에 `-Pandroid.testInstrumentationRunnerArguments.importPickerProbe=true`를 전달해 실행한다.

차량 관리 JSON에 불완전한 소모품 주기가 있으면 미리보기에서 건수를 알리고, 가져온 뒤 소모품 목록에도 설정 확인 안내를 표시한다. 호환성을 위해 원본 값은 자동 수정하지 않는다. 다른 계산 가능한 주기가 표시되어도 안내된 설정은 별도로 확인해야 한다.

개월 또는 가동시간 주기의 마지막 교체일이 없으면 사용자가 확인한 날짜를 별도로 입력할 수 있다. 교체 주행거리는 유지하고 정비 이력은 생성하지 않으며 다른 화면에서 주기가 바뀌면 덮어쓰지 않는다.

이벤트 교환 초안은 `event.schema.json` v1과 `event-v2.schema.json` v2다. 앱의 이벤트 상세에서 JSON 파일을 공유하거나 Android 파일 선택기로 저장·가져올 수 있다. 공유 시 JSON과 정비 참고 리포트는 앱의 전용 캐시 파일에 기록하고 읽기 권한이 부여된 content URI로 전달한다. 공유 파일은 앱 캐시에 남을 수 있으며 Android가 캐시를 정리할 수 있다. 전용 AVD에서 다른 UID에 대한 URI 읽기 권한 부여와 회수를 확인했다. Android 공유 선택기를 거친 외부 수신 앱의 실제 파일 읽기와 앱별 호환성은 별도 확인이 필요하다. 각 차량과 기록은 UUID를 사용한다. 파일 차량 ID가 앱에 등록되어 있지만 선택한 차량과 다르면 이벤트는 파일의 차량에 저장하고 그 차량 이름과 UUID를 안내한다. 파일 차량 ID가 현재 앱에 없으면 두 ID를 보여 주고 사용자가 같은 차량임을 확인할 때에만 현재 차량에 연결한다. 원본 차량 ID는 별도로 저장하고 재내보내기에 보존한다. 차량을 자동으로 생성하거나 ID가 다른 차량을 자동 병합하지 않는다. 이벤트 UUID를 중복 방지 키로 쓰고 같은 ID의 내용이 같으면 건너뛰고 다르면 충돌로 처리한다. 신호는 이벤트 ID, 개별 시각, 이름을 키로 한다. ISO 8601 UTC로 교환하고 앱 내부 시간은 Unix epoch milliseconds다. 거리는 km, 연료는 L, 금액은 정수 KRW, 좌표는 WGS84 도, 비율은 %다. 수집 출처와 완료 상태를 보존한다. 가져온 출처는 파일의 주장으로 실차 여부가 검증된 것은 아니다. 앱의 타임라인·상세·정비 리포트는 `MOCK`을 시뮬레이션으로, `VEHICLE`을 실차 여부 미확인 기록값으로 표시한다. JSON 원본 코드는 변경하지 않는다. 발생 시점 스냅샷은 각 신호에서 발생 시각 이전 가장 가까운 값이며 각 원래 시각을 보존한다.

전용 Pleos AVD에서는 테스트 APK의 별도 UID Activity를 명시적으로 실행해 공유 Intent에 부여된 권한으로 리포트와 JSON의 시험 내용을 실제로 읽는 것도 확인했다. 수신 Activity는 테스트 APK에만 포함된다. 이 시험은 공유 선택기를 통한 사용자 선택이나 실제 정비 앱별 호환성을 확인하지 않는다.

공유 선택기를 자동화하는 별도 진단은 전용 Pleos AVD에서 테스트 수신 항목을 찾지 못했다. 초기 시험은 앱 화면이 활성화되지 않은 상태여서 실제 사용자 흐름과 차이가 있었고, 이후 Carlog Activity를 먼저 띄운 시험에서도 항목을 찾지 못했다. 마지막 시험에서 Android는 `com.android.intentresolver.ChooserActivityLauncher`를 처리기로 확인했지만 접근 가능한 창 목록에 선택기 창은 보이지 않았다. 이 관찰만으로 선택기가 나타나지 않은 이유나 실제 앱 공유 성공 여부를 단정할 수 없다. 진단은 일반 시험에서 건너뛰며 다음 명령으로 명시적으로 실행한다. 실패 시에도 에뮬레이터 시험 스크립트의 시간 제한과 정리가 적용된다.

```bash
CARLOG_PLEOS_MAX_SECONDS=180 ./scripts/pleos-emulator-test.sh :app:connectedDebugAndroidTest \
  '-Pandroid.testInstrumentationRunnerArguments.class=kr.carlog.pleos.ShareFilesTest#androidChooserDeliversReportToSeparateTestApp' \
  -Pandroid.testInstrumentationRunnerArguments.shareChooserProbe=true
```

수집 중 동일 키의 값과 단위가 같은 신호는 버퍼와 저장소에서 한 번만 보존한다. 버퍼에 남아 있는 같은 키의 값이나 단위가 다르면 기존 값을 덮어쓰지 않고 수집과 진행 중인 이벤트를 중단한다. 버퍼 밖의 신호가 저장소의 기존 값과 충돌하면 해당 저장 묶음을 되돌리고 진행 중인 이벤트를 중단한다. 발생 시각이 같은 여러 값을 모두 보존하는 형식은 현재 지원하지 않는다.

실시간 신호의 이름은 공백만으로 구성할 수 없고 Unicode 코드 포인트 기준 256자 이하여야 하며 단위는 같은 기준으로 64자 이하여야 한다. 값은 유한한 숫자여야 한다. 이 조건을 위반하면 해당 신호를 버퍼와 저장소에 넣지 않고 수집과 진행 중인 이벤트를 중단한다. 이 검사는 단위나 센서 값의 물리적 정확성을 보증하지 않는다.

실시간 수집에서는 신호 시각이 기기 시각보다 2초를 초과해 앞서면 버퍼에 넣지 않고 수집을 중단하며 진행 중인 이벤트를 interrupted로 표시한다. 2초까지는 허용한다. 이는 버퍼를 보호하기 위한 현재 앱의 정책이며 Pleos SDK의 시간 정확도를 보증하지 않는다. 실차 연결 전에 신호의 측정·수신 시각과 기기 시계의 관계를 검증해야 한다. JSON 가져오기에는 이 실시간 기준을 적용하지 않고 이벤트 전후 60초 범위를 검사한다.

기기 시간 변경으로 이벤트 중단을 저장하던 작업이 취소되면 수집기를 정지하고 남은 중단 저장을 재시도한다. 저장소 오류가 계속되면 기록이 수집 중 상태로 남을 수 있으며 다음 앱 시작의 복구가 필요하다.

지도 앱에는 발생 시각 이전의 같은 이벤트·같은 시각·같은 시각 종류의 위도와 경도 중 가장 최근의 유효한 쌍만 전달한다. 두 종류가 모두 미확인인 기존 기록도 같은 종류로 취급한다. 두 단위는 `deg`, 위도는 −90~90, 경도는 −180~180이어야 한다. 시각이나 시각 종류가 다른 신호는 합치지 않으며, 쌍이 없으면 원본 신호를 보존하고 지도 표시 불가를 알린다. 리포트에는 선택된 좌표와 기록 시각·시각 종류를 표시한다. 시각이 같아도 별도로 수신된 좌표의 원래 측정 시점이 같다는 뜻은 아니며 이 검사는 실제 위치의 정확성이나 출처를 보증하지 않는다.

정비 참고 리포트는 이벤트·신호·연결 정비의 시각을 UTC ISO 8601 형식으로 표시해 밀리초 정보를 보존한다. 앱 화면의 날짜 표시는 기기의 로컬 시간이며 초 단위다. 리포트의 출처는 저장된 주장이고 실차 신호나 진단 결과로 인증된 것은 아니다.

수집 중 리포트는 미리보기를 연 시점까지의 내용이며 이후 자동으로 갱신되지 않는다. 리포트는 중단과 종료도 구분하고, 종료가 모든 신호의 전후 구간 확보를 뜻하지 않는다고 표시한다. 발생 시점 스냅샷은 발생 시각 또는 그 이전 마지막 관측값과 그 관측 시각이다.

리포트 미리보기의 파일 저장은 Android 문서 생성 선택기로 사용자가 정한 위치에 미리보기와 동일한 UTF-8 텍스트를 기록한다. 선택 취소 또는 선택기 실행 실패는 저장 상태를 해제한다. 파일을 선택하고 쓰는 동안 차량 전환과 중복 저장을 막으며 쓰기 실패 시 일부 내용이 남을 수 있다. 전용 AVD의 시험은 결과 URI 또는 출력 스트림을 직접 제공했으며 Pleos 파일 선택기의 실제 표시·선택은 미검증이다.

전용 Pleos AVD v2.1.0에서 Carlog Activity가 실행 중일 때 동일한 `CreateDocument("text/plain")` Intent를 시작하는 선택형 진단은 접근 가능한 창에서 처리기 창을 찾지 못해 실패했다. Android가 확인한 처리기는 `com.android.car.frameworkpackagestubs.Stubs$DocumentsUIStubWithResult`였다. 이 관찰만으로 원인이나 실제 사용자 선택·저장 가능 여부를 단정할 수 없다. 파일은 생성하지 않았으며 이 진단은 기본 계측 시험에서 건너뛴다.

별도로 테스트 APK의 다른 UID Activity가 같은 종류의 텍스트 문서 생성 Intent를 시작한 시험에서는 15초 안에 URI 없는 `RESULT_CANCELED`가 반환됐다. 테스트 APK에서만 관찰한 결과이며 Carlog 화면에서의 콜백이나 다른 차량의 동작을 보증하지 않는다. Carlog ViewModel의 취소 상태 해제는 결과를 직접 전달한 별도 시험으로 확인했다.

전용 AVD의 Compose 테스트 호스트에 Carlog 화면과 인메모리 DB를 띄운 별도 시험에서는 리포트의 파일 저장 버튼을 누른 뒤 취소 또는 사용 불가 안내가 표시되고 저장 대기가 해제됐다. 테스트 데이터를 사용했으며 실제 문서 선택과 파일 생성은 확인하지 않았다. 다른 차량의 동작을 보증하지 않는다.

```bash
CARLOG_PLEOS_MAX_SECONDS=180 ./scripts/pleos-emulator-test.sh :app:connectedDebugAndroidTest \
  '-Pandroid.testInstrumentationRunnerArguments.class=kr.carlog.pleos.ShareFilesTest#documentPickerReturnsResultProbe' \
  -Pandroid.testInstrumentationRunnerArguments.reportPickerResultProbe=true
```

```bash
CARLOG_PLEOS_MAX_SECONDS=180 ./scripts/pleos-emulator-test.sh :app:connectedDebugAndroidTest \
  '-Pandroid.testInstrumentationRunnerArguments.class=kr.carlog.pleos.ShareFilesTest#androidDocumentPickerShowsForReport' \

```

리포트 준비 시 이벤트 상태·신호·현재 등록 차량 정보·같은 차량의 활성 연결 정비를 하나의 Room 트랜잭션으로 읽는다. 화면에 각각 표시 중인 목록의 갱신 시점에 의존하지 않으며, 준비 중에는 차량 전환과 중복 공유를 차단한다. 이 스냅샷은 수집 중인 신호의 미래 값을 예측하지 않는다.

리포트는 각 신호의 이름·단위·시각 종류별로 발생 전·시점 및 이후 표본 수와 최초·최종 관측 시각을 표시한다. 이 범위는 연속 수집을 보장하지 않는다. 신호별 범위 항목은 최대 100개를 표시하고 추가 항목 수를 밝힌다. 생략은 리포트 표시만 제한하며 원본 신호는 유지한다.

가져오기는 쌍이 맞지 않는 UTF-16 대리 코드, 중복 객체 필드, 잘못된 JSON 문법, 64단계가 넘는 중첩, v1에서 정의하지 않은 필드, 진행 중인 이벤트, UTC가 아닌 시각, UTC 연도 0001~9999 밖의 시각, 밀리초보다 정밀한 시각, 이벤트 전후 60초 밖의 신호, 중복 신호 키, 1만 개가 넘는 신호 또는 5 MiB가 넘는 파일을 거부한다. 같은 연도 제한을 내보내기에도 적용하며 범위 밖 기존 기록은 유지한다. 중복 이름 검사는 이스케이프를 해석한 뒤 같은 객체 안에서 수행한다. 이 제약은 로컬 데이터 손실이나 모호한 병합을 막기 위한 현재 앱 구현의 제한이며, JSON Schema 자체보다 엄격하다. 파일을 변환할 때는 원본을 보존해야 한다.

이벤트 및 차량 관리 JSON은 초를 포함한 UTC 시각을 요구하며 윤초 `:60`과 `24:00`을 거부한다. 이 표현을 Java 기본 파서처럼 다른 시각으로 정규화하지 않는다. 원본 파일은 유지하고 발신 측에서 정확한 시각 표현을 확인해야 한다.

교환 예시는 [`examples/event-v1.json`](examples/event-v1.json)이다. Schema의 `format` 검사는 검증기에서 명시적으로 활성화해야 할 수 있다. Schema는 시간 정밀도, 신호별 이벤트 전후 범위, `(timestamp, name)` 중복, 파일 크기, 중복 JSON 필드와 공백만으로 된 이름을 모두 검증하지 못한다. 문자열 길이는 Schema와 앱 모두 Unicode 코드 포인트 기준이다. Schema 통과만으로 앱 가져오기 성공을 보장하지 않는다.

v1과 [v2](event-v2.schema.json)의 신호 값은 숫자만 허용한다. 주행 모드·방향지시등·오일 상태 같은 SDK enum은 아직 넣지 않는다. Room v9는 신호의 시각 종류를 측정(`MEASURED`), 수신(`RECEIVED`), 미확인(null)으로 저장하며 기존 기록과 v1 가져오기는 미확인으로 유지한다. v2는 모든 신호에 필수 `timestampKind` 필드를 두고 이 세 값을 보존한다. 앱은 시각 종류가 명시된 신호가 있으면 v2로 내보내고, 모두 미확인이면 기존 v1로 내보낸다. v1만 지원하는 수신자는 v2를 지원하도록 변경해야 한다. [v2 예시](examples/event-v2.json)는 시험용 데이터다. 별도 실험 모듈은 SDK enum 이름과 SDK 버전, 수신 시각을 보존하지만 앱에 연결되지 않았다. 향후 상태형 값도 보존할 교환 계약이 필요하다.

내보내기는 화면에 표시 중인 목록 대신 Room 트랜잭션으로 이벤트의 현재 상태와 저장된 신호를 함께 읽고, 같은 앱의 가져오기 검증과 UTF-8 크기 제한을 통과하는 경우에만 진행한다. 조건을 만족하지 못하는 기존 이벤트는 삭제하거나 잘라 내지 않고 오류를 표시한다. 신호 1만 개 또는 5 MiB를 초과한 이벤트의 분할 교환은 아직 지원하지 않는다.

신호 개수와 파일 크기 제한은 서로 다른 안내로 표시한다. 두 경우 모두 원본 이벤트·신호를 유지하며 정비 참고 리포트를 별도로 확인할 수 있다. 다른 형식 오류는 일반 오류로 안내한다.

이벤트의 분류와 메모를 수정해도 이벤트 ID와 수집 신호는 유지된다. v1에는 이벤트 수정 시각이나 revision이 없어 수정 전후 파일을 같은 ID의 서로 다른 내용으로 판단한다. 이미 가져온 쪽에서는 자동으로 덮어쓰지 않고 충돌로 표시하므로 사용자는 양쪽 원본을 보존해야 한다. 향후 양방향 동기화에는 revision과 충돌 해결 정책이 필요하다.

앱 내 이벤트 편집은 편집을 시작할 때의 분류와 메모가 저장 시에도 일치할 때만 갱신한다. 불일치하면 입력을 유지하고 최신 내용을 확인하도록 안내한다. 수집 상태와 신호가 바뀌는 것만으로는 충돌시키지 않는다. 이는 같은 로컬 데이터베이스의 값 비교이며 기기 간 revision이나 동기화 충돌 해결을 제공하지 않는다.

## 차량 관리 기록 교환

차량 앱은 현재 차량의 활성 주행거리·주유·정비·지출 기록과 활성 소모품 주기를 [`vehicle-records-v1.schema.json`](vehicle-records-v1.schema.json) 형식으로 저장할 수 있다. [예시](examples/vehicle-records-v1.json)는 시험용이다. 차량과 각 기록·주기의 UUID, 개별 기록 일시와 입력값을 내보내며 Room 트랜잭션에서 읽은 한 시점의 스냅샷이다. 일시는 UTC ISO 8601, 거리는 km, 주유량은 L, 금액은 정수 KRW다. 주행거리 미입력은 `odometerKm: null`이고 0과 구분된다. 지출 `category`에는 차량 앱의 원래 표시값을 보존하고 알려진 PWA 분류만 `expenseCategoryCode`로 대응한다. 알 수 없는 분류 코드는 null이며 원래 표시값은 남긴다.

파일은 최대 5 MiB이며 JavaScript의 안전한 정수 범위를 벗어난 금액·월 주기, 표현할 수 없는 날짜, 유효하지 않은 UUID·숫자·Unicode가 있으면 저장을 거부한다. 저장 전 같은 앱의 가져오기 검증도 실행하므로 UUID 정규화 후 중복처럼 다시 읽을 수 없는 파일은 생성하지 않는다. 이 검사는 차량 일치나 연결 이벤트 존재 여부를 보장하지 않는다. 스키마만으로는 공백만 있는 이름, 데이터 간 상호 관계, 파일 크기와 모든 앱 검증을 표현하지 못한다. 삭제된 항목과 이벤트·신호는 포함하지 않고 정비의 `relatedEventId`는 참조만 남긴다. 따라서 이 파일은 전체 백업이나 삭제 전파용 동기화 기록이 아니다. 차량 앱은 같은 차량 UUID와 동일한 차량 정보에 한해 미리보기 후 이 형식을 가져온다. 동일한 기록은 건너뛰고, 내용이 다른 ID나 삭제 표시와 충돌하면 전체 가져오기를 취소한다. 정비 기록에 연결된 이벤트는 같은 차량에 먼저 가져와야 한다. 누락된 서로 다른 이벤트 수와 최대 3개의 ID를 표시하며, 모든 기록은 저장하지 않고 미리보기를 유지한다. 다른 차량으로의 매핑과 PWA의 이 형식 가져오기는 아직 지원하지 않는다. 새 기기에서는 Mock 수집을 중단한 뒤 파일 미리보기에서 원본 UUID의 차량을 별도로 등록·선택하고 가져오기 적용을 누를 수 있다. 기존 차량은 보존되며 다른 차량으로 합치지는 않는다. 정비에 연결된 이벤트는 같은 차량 선택 후 이벤트 JSON으로 먼저 가져와야 한다. 원본 데이터와 파일을 보관한다. 앱은 금액·월 주기·연식에 JSON 정수 표기만 허용하므로 JSON Schema가 허용하는 `1.0` 같은 표기는 거부한다. **PWA의 기존 백업 복원에 넣지 않는다.** 이벤트는 별도의 이벤트 JSON으로 내보낸다.

기존 PWA 백업은 `app=carlog`, `schemaVersion=1` 및 `data.vehicles`, `fuelLogs`, `maintenanceLogs`, `expenseLogs`, `odometerReadings`, `maintenanceSchedules`를 사용한다. 차량 ID, 날짜, 주행거리, 주유량/가득 여부/비용, 정비 항목과 비용, 지출 분류와 금액을 각각 명시적으로 매핑해야 한다. 현재 앱은 정비의 다중 항목과 영수증 등 모든 필드를 매핑하지 않으므로 무손실 PWA 교환을 지원하지 않는다. PWA 백업 import는 기존 데이터를 전부 대체하므로 앱에서 호출하거나 수정하지 않는다. 실제 이관은 원본 백업 보존, 별도 변환기와 검증, 충돌 미리보기, 테스트 복원 후 도입한다.

### PWA v1 필드 대응 초안

아래 표는 향후 변환기를 만들 때의 대응 관계이며, 현재 읽기 전용 미리보기가 데이터를 저장한다는 뜻은 아니다. 원본 테이블과 원본 ID를 별도로 보존하고, 대상의 동일 ID가 다른 내용과 충돌하면 덮어쓰지 않고 사용자에게 알려야 한다. 서로 다른 PWA 테이블에서 같은 ID가 나올 수 있으므로 단일 `RecordEntity`에 합칠 때 아래 결정적 ID 규칙을 적용한다. 실제 변환 결과에 원본 데이터셋·테이블과 ID를 저장하는 스키마는 아직 필요하다.

차량 앱의 `pwaRecordId`는 고정 namespace `c7e2b663-29fa-48ab-aac0-0c62a2a1074a`와 UTF-8 이름 `pwa-v1/{dataset-uuid}/{table}/{original-id}`를 사용한 UUID v5다. `dataset-uuid`는 소문자 하이픈 UUID, `table`은 `fuelLogs`, `maintenanceLogs`, `expenseLogs`, `odometerReadings` 중 하나이며 원본 ID는 정규화하거나 대소문자를 바꾸지 않는다. 이 규칙은 서로 다른 테이블과 데이터셋의 동일 ID를 구분하고 같은 원본을 다시 변환할 때 같은 ID를 만든다. 동일 ID라도 내용이 다르면 충돌이며 자동 덮어쓰지 않는다. SHA-1 UUID의 충돌 가능성은 0이 아니므로 향후 가져오기는 원본 참조와 내용을 함께 대조한다.

기존 PWA 백업에는 이 규칙의 `dataset-uuid`가 없다. 향후 이관 기능은 사용자가 같은 원본이라고 확인한 백업들에 대해 단일 UUID를 생성·보존하고, 다른 원본과의 연결은 명시적으로 확인해야 한다. 백업마다 임의 UUID를 새로 만들거나 파일 내용만으로 같은 원본 여부를 추정하면 중복 방지가 깨진다. 현재는 ID 생성 함수와 시험만 있으며 데이터셋 등록, 원본 참조 저장, 변환·가져오기는 구현되지 않았다.

| PWA | 차량 앱의 대응 필드 | 이관 전 해결할 차이 |
| --- | --- | --- |
| `vehicles`: `id`, `nickname`, `initialOdometer`, `maker`, `model`, `year`, `fuelType` | `VehicleEntity.id`, `name`, `initialKm`, `maker`, `model`, `year`, `fuelType` | 차량 앱의 추가 정보는 선택값이며 번호판·탱크 용량 등은 아직 저장할 수 없다. |

PWA 날짜 문자열은 타임존 정보가 있는 ISO 8601인 경우 해당 순간을 UTC epoch milliseconds로 변환한다. 타임존이 없거나 유효하지 않은 날짜, 정수가 아닌 금액, 범위를 벗어나는 값은 조용히 기본값으로 바꾸지 않고 변환 오류로 표시한다. 영수증과 사용자 정의 항목은 원본 백업에 보존하고, 대상이 해당 정보를 저장할 수 있기 전까지 무손실 이관이라고 표시하지 않는다.

PWA 지출 분류는 코드이고 현재 차량 앱은 한글 표시값을 저장한다. 대응은 `insurance`→보험, `tax`→세금, `parking`→주차, `toll`→통행료, `wash`→세차, `fine`→과태료, `accessory`→용품, `etc`→기타다. PWA의 `fine` 표시명은 과태료/범칙금이지만 차량 앱에는 과태료로 표시한다. 앱의 `PwaExpenseCategory.kt`는 알려진 값만 양방향 매핑하며 알 수 없는 코드는 null을 반환한다. 변환기는 원본을 보존하고 알 수 없는 값을 사용자에게 알려야 하며 임의로 `etc`로 바꾸면 안 된다. 이 함수는 저장이나 실제 백업 이관을 수행하지 않는다.

차량 앱의 PWA 백업 미리보기는 최대 25 MiB의 v1 백업을 읽어 차량별 주유·정비·지출 수와 삭제 표시, 누락·중복 ID, 누락된 차량 참조, 영수증·사용자 항목 수, 분류를 확인할 수 없는 활성 지출 수를 표시한다. 중복 객체 필드, 잘못된 Unicode와 64단계가 넘는 중첩을 거부한다. 이것은 구조와 연결의 일부만 검사하며 전체 레코드의 유효성 검증이나 데이터 이관을 수행하지 않는다. 백업의 영수증 등은 원본에만 남으므로 백업 파일을 보존한다.

활성 정비 기록의 `items`가 비어 있지 않은 객체 배열이면 복수 항목 여부를 집계한다. 배열이 없거나 비어 있거나 객체가 아닌 항목을 포함하면 배열 확인 불가로 센다. 항목의 필드나 금액은 이 집계로 검증하지 않는다. 정비 테이블이 누락된 경우 건수는 확인 불가이며 복수 항목의 무손실 이관은 지원하지 않는다.

활성 주행거리 기록은 직접 입력, 주유·정비·지출 파생, 알 수 없는 출처로 나누어 센다. 파생 기록의 `refId`가 해당 출처 테이블의 같은 차량에 속한 활성 원본 하나를 가리키지 않으면 연결 확인 불가로 센다. 같은 차량의 같은 원본 ID가 중복된 경우도 연결 확인 불가다. 삭제된 주행거리와 삭제된 원본은 각각 활성 기록과 연결 가능한 원본에서 제외한다. 이 검사는 연결 존재 여부만 확인하며 원본과 주행거리·일시의 일치나 실제 이관 가능성을 보증하지 않는다.

원본이 유일한 활성 기록으로 확인되는 파생 주행거리들에 한해, 같은 차량·출처·원본 ID를 가리키는 두 번째 이후 기록 수를 별도로 표시한다. 삭제된 파생 기록과 연결이 모호하거나 없는 원본은 이 중복 수에서 제외하며, 값이 같은지 또는 실제로 삭제해야 할 기록인지는 판단하지 않는다. 필요한 테이블이 누락되면 전체 확인 불가로 표시한다.

### 향후 동기화 경계 초안

`SyncContract.kt`는 네트워크에 연결되지 않은 전송 인터페이스 초안이다. Supabase 클라이언트·서버 테이블·로그인·동기화 작업이나 Room outbox는 아직 없다. 구현 전에 실제 PWA 스키마 및 서버 능력에 맞춰 계약을 검토해야 하며, 현재 인터페이스가 동기화 동작을 보장하지는 않는다.

- 기록 키는 컬렉션과 UUID를 함께 사용한다. 이벤트 JSON v1의 `id`와 같은 개념의 식별자를 쓰되 JSON 파일 자체를 동기화 프로토콜로 취급하지 않는다. 한 요청 묶음에 같은 기록의 변경을 여러 개 넣지 않는다.
- 각 변경은 재시도해도 바뀌지 않는 별도 mutation UUID를 갖는다. 서버 구현은 인증된 사용자 범위에서 mutation UUID와 요청 내용·결과를 원자적으로 기록해 동일 요청 재시도에 같은 결과를 반환하고, 같은 UUID의 다른 내용은 거부해야 한다.
- 새 기록은 `CreateOnly`, 기존 기록의 수정·삭제는 `IfMatch(serverRevision)` 조건을 사용한다. revision은 서버 발급 불투명 값이며 기기 시계나 `updatedAt`으로 우선순위를 정하지 않는다. 삭제는 조건부 tombstone으로 전달하고, 서버와 모든 클라이언트의 보존 기간·삭제 전파 정책을 정하기 전에는 실제 삭제를 구현하지 않는다.
- 각 제출 ID에 대해 적용·충돌·거부 결과가 정확히 하나씩 있어야 한다. 누락·중복·예상 외 ID가 있는 응답은 전체 확인을 보류한다. 충돌 시 로컬 변경과 서버 상태를 보존하고 사용자에게 해결을 요청할 수 있도록 한다. 자동 덮어쓰기나 단순 최신 시각 우선 정책은 적용하지 않는다.
- 내려받기는 불투명 cursor와 `hasMore`로 페이지를 구분한다. 원격 변경 적용과 cursor 저장은 동일 로컬 트랜잭션에서 성공해야 한다. 진행 중 이벤트는 업로드하지 않으며 완료된 이벤트와 신호의 일관된 스냅샷이 필요하다. 초기 전체 조회, 여러 페이지에 걸친 변경, 중복 수신 및 재시작 복구를 구현 전에 검증해야 한다.
- 업로드 payload는 수집 위치·메모 등 민감한 내용을 포함할 수 있다. 인증·차량별 접근 제어·명시적 동의·전송 및 저장 보호·보존과 삭제 정책을 먼저 확정한다. 인터페이스의 `toString()`은 payload 내용을 출력하지 않지만, 전송·로그·오류 보고의 보안을 보장하는 것은 아니다.

현재 `VehicleEntity`와 이벤트에는 동기화에 필요한 모든 변경 이력·revision·삭제 시각이 없다. 주유·정비·지출 모델도 PWA와 완전히 대응하지 않는다. 서버의 조건부 쓰기·멱등성과 로컬 outbox, 원본 참조 및 충돌 UI를 구현·검증하기 전에는 Supabase에 연결하거나 자동 동기화를 활성화하지 않는다.

### 새 기기에서 차량 관리 기록 가져오기

차량 관리 JSON v1은 원본 차량 UUID 하나만 담으며 삭제된 기록과 이벤트를 포함하지 않는다. 따라서 전체 백업 복원이 아니다. 파일 미리보기에서 Mock 수집을 중단한 뒤 파일 차량 등록·선택을 확인하면 원본 UUID의 차량이 별도로 생성되거나 동일한 차량이 선택된다. 같은 UUID에 다른 차량 정보가 이미 있으면 덮어쓰지 않는다. 이후 사용자가 가져오기 적용을 누르면 기록과 주기가 트랜잭션으로 추가된다. 연결된 이벤트는 별도 JSON으로 먼저 가져와야 한다. 전용 AVD에서는 서로 다른 차량의 기존 데이터가 있는 상태에서 누락 이벤트로 정비 적용이 거부되는 것, 이벤트 가져오기 후 정비 재시도와 두 UUID의 재내보내기를 확인했다. 시험 파일은 생성한 데이터이며 실제 사용자 백업 이관을 증명하지 않는다.

차량 전환은 수집 중이거나 저장·가져오기 작업, 다른 차량 화면, 미완료 이벤트가 있을 때 차단한다. 기존 차량과 기록은 삭제하지 않으며 화면에서 다시 선택할 수 있다. 선택은 Room v11에 보존된다. 작성 중인 입력은 전환 시 지워지므로 확인 대화상자에서 안내한다. 다른 차량 UUID로의 데이터 병합, 삭제 기록 전파 및 PWA의 해당 파일 가져오기는 지원하지 않는다.
